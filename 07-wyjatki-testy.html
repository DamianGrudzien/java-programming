Wyjątki & Testy

Solidna obsługa błędów i automatyczne testy jednostkowe to podstawa profesjonalnego kodu. JUnit 5 + Mockito to standard w Javie.

Hierarchia Wyjątków

Hierarchia
Throwable
├── Error                    // Błędy JVM — nigdy nie łap!
│   ├── OutOfMemoryError
│   └── StackOverflowError
└── Exception
    ├── Checked Exceptions      // Kompilator wymaga obsługi
    │   ├── IOException
    │   ├── SQLException
    │   └── ParseException
    └── RuntimeException        // Unchecked — opcjonalna obsługa
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        └── IndexOutOfBoundsException
💡
Checked vs Unchecked: Checked — gdy klient może sensownie obsłużyć błąd (np. brak pliku). Unchecked (RuntimeException) — błędy programisty (null, zły indeks). W nowoczesnym Javie preferuje się unchecked dla logiki domenowej.

Dobre Praktyki Obsługi Wyjątków

Wyjątki — co robić, czego nie robić
// ❌ ANTY-WZORZEC 1 — pusty catch (błąd znika!)
try { operacja(); } catch (Exception e) { }

// ❌ ANTY-WZORZEC 2 — łapanie zbyt szerokiego typu
catch (Exception e) { e.printStackTrace(); } // łapiemy za dużo

// ✅ try-with-resources — automatyczne zamknięcie zasobu (Java 7+)
try (var reader = new BufferedReader(new FileReader(plik));
     var conn   = dataSource.getConnection()) {

    String linia = reader.readLine();
    // close() na reader i conn wywołane automatycznie!

} catch (IOException e) {
    log.error("Błąd odczytu pliku: {}", plik.getName(), e);
    throw new PlikNieOdczytalnyException("Nie można odczytać: " + plik, e);
}

// ✅ Multi-catch — kilka typów w jednym catch
try {
    parsujIZapisz(dane);
} catch (ParseException | IOException e) {
    throw new PrzetwarzanieException("Błąd przetwarzania danych", e);
}

// ✅ Własny wyjątek z kontekstem
public class UzytkownikNieIstnieje extends RuntimeException {
    private final long userId;

    public UzytkownikNieIstnieje(long id) {
        super("Użytkownik id=" + id + " nie istnieje");
        this.userId = id;
    }
    public long getUserId() { return userId; }
}

Testy Jednostkowe — JUnit 5

Testy jednostkowe weryfikują działanie izolowanych fragmentów kodu (klasa, metoda). Standard w Javie: JUnit 5 + Mockito do mockowania zależności.

💡
Wzorzec AAA: Każdy test ma trzy sekcje — Arrange (przygotuj dane), Act (wywołaj metodę), Assert (sprawdź wynik). Jeden test = jedna weryfikacja.
JUnit 5 + Mockito
@ExtendWith(MockitoExtension.class)
class ZamowienieSerwisTest {

    @Mock
    private UzytkownikRepo uzytkownikRepo;   // automatyczny mock

    @Mock
    private PlatnoscSerwis platnoscSerwis;

    @InjectMocks
    private ZamowienieSerwis sut;            // System Under Test

    @Test
    @DisplayName("Powinien złożyć zamówienie gdy użytkownik istnieje")
    void powinienZlozycZamowienie() {
        // Arrange
        var uzytkownik = new Uzytkownik(1L, "Anna");
        when(uzytkownikRepo.znajdz(1L))
            .thenReturn(Optional.of(uzytkownik));
        when(platnoscSerwis.przetworz(anyDouble())).thenReturn(true);

        // Act
        Zamowienie wynik = sut.zloz(1L, 299.99);

        // Assert
        assertNotNull(wynik);
        assertEquals(Status.POTWIERDZONE, wynik.getStatus());
        verify(platnoscSerwis).przetworz(299.99); // weryfikuj wywołanie
        verifyNoMoreInteractions(platnoscSerwis);
    }

    @Test
    @DisplayName("Powinien rzucić wyjątek gdy brak użytkownika")
    void powinienRzucicWyjatekGdyBrakUzytkownika() {
        // Arrange
        when(uzytkownikRepo.znajdz(99L)).thenReturn(Optional.empty());

        // Act + Assert — jeden wiersz!
        assertThrows(UzytkownikNieIstnieje.class, () -> sut.zloz(99L, 50.0));
    }

    // Parameterized Test — jeden test, wiele wartości
    @ParameterizedTest
    @ValueSource(doubles = {-1, 0, -999})
    @DisplayName("Powinien odrzucić nieprawidłową kwotę")
    void powinienOdrzucicNieprawidlowaKwote(double kwota) {
        assertThrows(IllegalArgumentException.class,
            () -> sut.zloz(1L, kwota));
    }
}

Zasady FIRST dla Testów

⚡
Fast — Szybkie
Testy muszą działać szybko. Setki testów powinny kończyć się w sekundy. Powolne testy są pomijane.
🔒
Independent — Niezależne
Kolejność uruchomienia nie powinna mieć znaczenia. Każdy test zakłada czysty stan.
🔄
Repeatable — Powtarzalne
Ten sam wynik niezależnie od środowiska. Żadnych zależności od czasu, sieci, danych zewnętrznych.
✅
Self-validating
Test sam sprawdza wynik. Żadnych manualnych inspekcji — pass lub fail, nic pomiędzy.
⏰
Timely — Terminowe
Pisane razem z kodem (TDD) lub zaraz po. Testy pisane po miesiącu tracą wartość.
